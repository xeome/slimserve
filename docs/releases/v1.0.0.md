# SlimServe 1.0.0

SlimServe 1.0.0 is a rewrite in Elixir, on Phoenix LiveView. It replaces the Go app, whose last
release is v0.3.2. Listings update live as files change, images get thumbnails and an inspector,
and one write password turns on uploads, new folders, renames, moves and deletes from the browser.
It serves a local folder or an S3 bucket.

The configuration changed. Read the settings table below before you move a Go deployment to 1.0.0.

## Images and chart

The image is `ghcr.io/xeome/slimserve`, built for linux/amd64 only. This release is tagged `1.0.0`,
`1.0`, `1`, `latest`, `v1.0.0`, `v1.0` and `v1`. The Go app stays on `0`, `0.3` and `v0.3.2`, so pin
one of those to keep running it. 1.0.0 has no arm64 image, so `latest` stops pulling on an arm64
host. Pin `v0.3.2` there.

The Helm chart is `oci://ghcr.io/xeome/slimserve-helm`, version 2.0.0. Its default image is
`ghcr.io/xeome/slimserve:1.0.0`.

## Settings that refuse to start

SlimServe 1.0 reads only environment variables. It refuses to start, and names what it found, when
one of these is present:

- `CONFIG_FILE`, `SLIMSERVE_CONFIG` or `SLIMSERVE_IGNORE_PATTERNS` is set;
- a file exists at `/etc/slimserve/config.json`;
- a file exists at `/data/slimserve.json`, whatever the storage;
- on local storage, a `slimserve.json` exists in the served folder.

The Go app read its config file from `SLIMSERVE_CONFIG`, or from `slimserve.json` in its working
directory, which was `/data` in the image. SlimServe 1.0 would serve that file as a plain file,
logins included, so it refuses instead. Move the settings into environment variables, and move the
file out of `/data` and the served folder.

The Go app's command-line flags, `--config` among them, are gone too. So remove a Compose
`command:` or a Helm `args:` override that passes them.

The Go app never loaded `CONFIG_FILE` or `/etc/slimserve/config.json`. Its image only printed which
file it would use. They are refused all the same, because a deployment that sets them expects them
to work. For `SLIMSERVE_IGNORE_PATTERNS`, put a `.slimserveignore` file in the folder instead: its
gitignore-style patterns hide matching names in that folder and everything below it.

## Settings

Every setting the Go app read, with its Go default, and what to set for SlimServe 1.0. A setting
marked "not supported" is ignored, unless the table says it refuses to start.

| Go setting | Go default | SlimServe 1.0 |
| --- | --- | --- |
| `SLIMSERVE_HOST` | `0.0.0.0` | Not supported. It listens on every interface. |
| `SLIMSERVE_PORT` | `8080` | `PORT`, `8080` in the image. |
| `SLIMSERVE_STORAGE_PATH` | `.` (`/data` in the image) | `SLIMSERVE_ROOT`, `/data` in the image. With S3, `SLIMSERVE_S3_BUCKET`. |
| `SLIMSERVE_STORAGE_TYPE` | `local` | `SLIMSERVE_STORAGE`. See the line below. |
| `SLIMSERVE_STORAGE_TYPE=s3` | | Ignored: SlimServe 1.0 then serves the local `/data`, which is empty in a fresh container. Set `SLIMSERVE_STORAGE=s3`. |
| `SLIMSERVE_S3_REGION` | unset | `AWS_REGION`, default `us-east-1`. |
| `SLIMSERVE_S3_ENDPOINT` | AWS | `AWS_ENDPOINT_URL_S3`. Requests are path-style. |
| `SLIMSERVE_S3_ACCESS_KEY` | unset | `AWS_ACCESS_KEY_ID`. |
| `SLIMSERVE_S3_SECRET_KEY` | unset | `AWS_SECRET_ACCESS_KEY`. |
| `SLIMSERVE_S3_PREFIX` | unset | Not supported. The whole bucket is served. |
| `SLIMSERVE_DISABLE_DOTFILES` | `true` | Not supported. Hidden files are never listed or served. |
| `SLIMSERVE_LOG_LEVEL` | `info` | Not supported. |
| `SLIMSERVE_ENABLE_AUTH` | `false` | Not supported. Setting both `SLIMSERVE_USERNAME` and `SLIMSERVE_PASSWORD` turns the login on. |
| `SLIMSERVE_USERNAME`, `SLIMSERVE_PASSWORD` | unset | The same names. Set both or neither, and a fixed `SECRET_KEY_BASE` with them. |
| `SLIMSERVE_THUMB_CACHE_MB` | `100` | The same name and default. |
| `SLIMSERVE_THUMB_JPEG_QUALITY` | `85` | Not supported. |
| `SLIMSERVE_CACHE_DIR` | `$TMPDIR/slimserve/thumbcache` | The same name, for the thumbnail cache. Default `$TMPDIR/slimserve-thumbs`. |
| `SLIMSERVE_THUMB_MAX_FILE_SIZE_MB` | `10` | The same name and default. |
| `SLIMSERVE_IGNORE_PATTERNS` | unset | Refuses to start. Use `.slimserveignore` files. |
| `SLIMSERVE_ENABLE_ADMIN` | `false` | Not supported. Setting `SLIMSERVE_WRITE_PASSWORD` turns on editing. |
| `SLIMSERVE_ADMIN_USERNAME` | unset | Not supported. The write login takes the viewer username when there is one. |
| `SLIMSERVE_ADMIN_PASSWORD` | unset | `SLIMSERVE_WRITE_PASSWORD`. It must differ from `SLIMSERVE_PASSWORD`. |
| `SLIMSERVE_MAX_UPLOAD_SIZE_MB` | `100` | `SLIMSERVE_UPLOAD_MAX_MB`, default `100`. |
| `SLIMSERVE_ALLOWED_UPLOAD_TYPES` | `*` | `SLIMSERVE_UPLOAD_TYPES`, the same comma-separated extensions. Leave it unset for any type, because `*` refuses to start. |
| `SLIMSERVE_MAX_CONCURRENT_UPLOADS` | `3` | Not supported. |
| `SLIMSERVE_CONFIG` | unset | Refuses to start. |
| `CONFIG_FILE` | `/etc/slimserve/config.json` | Refuses to start. |

New settings, such as `SLIMSERVE_HTTPS`, `PHX_HOST` and the thumbnail and download caches, are
listed in the [README](https://github.com/xeome/slimserve/blob/v1.0.0/README.md).

## Moving a Docker Compose deployment

1. Pin the image to `ghcr.io/xeome/slimserve:1.0.0`.
2. Remove the config file mount and every setting the table marks as refused, and rename the rest
   as the table says.
3. Delete the `healthcheck:` block. It runs `wget`, and the image has no `wget`.
4. With a login, add a fixed `SECRET_KEY_BASE` (`openssl rand -base64 48`).
5. Keep `./data:/data` and `user: "1001:1001"`. The image runs as the same uid and gid as the Go one.

## Moving a Helm release

Chart 2.0.0 upgrades a Go release in place and keeps its data. Follow "Upgrading from the Go chart"
in the [Helm guide](https://github.com/xeome/slimserve/blob/v1.0.0/manifests/helm/README.md#upgrading-from-the-go-chart),
then upgrade from `oci://ghcr.io/xeome/slimserve-helm --version 2.0.0`.

## How this release is cut

The Elixir history is pushed to `master`, and its CI run must pass. Only then is the tag `v1.0.0`
pushed, which runs the release pipeline: the image, then the chart, then this page, then the
moving tags such as `latest`. A transient failure in the promote job is recovered with
"Re-run failed jobs". A re-run uses the workflow at the tag, so a bug in promote's own steps
means moving the tags by hand.
