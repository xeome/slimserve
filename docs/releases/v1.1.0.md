# SlimServe 1.1.0

SlimServe 1.1.0 runs several replicas behind a proxy. The app answers health probes at
`/.app/healthz` and `/.app/readyz`, shuts down without dropping open downloads, reads the client
address from `X-Forwarded-For` past the proxies in `SLIMSERVE_TRUSTED_PROXIES`, and clusters on
one port, 4370, with no epmd.

The Helm chart is now version 3. It runs two shapes:

- Local storage: one replica by default, more on the same disk. Every pod runs on the node that
  holds the volume, and an upgrade replaces one pod at a time, so it no longer stops service.
- S3: two replicas by default, spread across nodes and zones, with a PodDisruptionBudget.

Every pod runs with a read-only root filesystem, as a non-root user with no capabilities, and
without an API token. Above one replica a NetworkPolicy keeps the cluster port to the release's
own pods. `existingSecret` reads the credentials from a Secret you manage. A values schema rejects
a misspelt key. The chart needs Kubernetes 1.30 or later.

## Upgrading from chart 2

Chart 3 needs the 1.1.0 image or later, for the new probe paths. It defaults to that image.

1. On S3, `replicas` now defaults to 2. Set `cluster.cookie` and `auth.secretKeyBase`, or
   `replicas: 1`.
2. Upgrade with `--reset-then-reuse-values` or `--reset-values -f values.yaml`. Never use
   `--reuse-values`: it drops the defaults of the new keys.
3. An S3 release that already ran several replicas does not cluster across its old and new pods
   during this one rollout, because the cluster port changes to 4370. On a CNI that enforces
   NetworkPolicy, the new policy also cuts the old pods' own cluster until they are gone. So a
   change made through an old pod may show late on another pod. When the upgrade finishes, run
   `kubectl rollout restart deployment/<release>-main -n <namespace>`: the fresh pods start with
   empty caches and cluster on 4370.
4. To switch from S3 to local storage in the same upgrade, scale to 0 first (`--set replicas=0`),
   at any replica count, then set the replica count again.

The [Helm guide](https://github.com/xeome/slimserve/blob/v1.1.0/manifests/helm/README.md) covers
both shapes, the drain and node-failure behaviour of local storage, and `existingSecret`.
